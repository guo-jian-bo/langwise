# 代码审查检查清单

基于项目全局规则第10章「代码复杂度管理」和第13章「代码质量检测与持续优化」

## 📋 审查前准备

- [ ] 运行 `./scripts/code_quality_check.sh` 自动化检查
- [ ] 运行 `flutter analyze` 检查静态分析
- [ ] 运行 `flutter test` 确保测试通过
- [ ] 检查 CI/CD 流水线状态

## 🔍 代码复杂度检查

### 圈复杂度检查
- [ ] 单个方法/函数的圈复杂度 ≤ 8
- [ ] 复杂的条件逻辑是否可以用策略模式替代
- [ ] 是否存在过多的 if-else 嵌套
- [ ] 是否可以使用早期返回减少复杂度

### 函数长度检查
- [ ] 方法长度 ≤ 15行（不包括空行和注释）
- [ ] 长函数是否可以拆分为多个小函数
- [ ] 每个函数是否只做一件事（单一职责）
- [ ] 函数命名是否清晰表达其功能

### 参数数量检查
- [ ] 方法参数 ≤ 3个
- [ ] 超过3个参数是否使用了配置对象封装
- [ ] 是否可以使用建造者模式减少参数
- [ ] 布尔参数是否使用了命名参数而非位置参数

### 嵌套深度检查
- [ ] 代码嵌套层级 ≤ 3层
- [ ] 是否使用了卫语句减少嵌套
- [ ] 是否可以用策略模式替代深层嵌套
- [ ] 复杂的条件判断是否可以提取为方法

### 类长度检查
- [ ] 类长度 ≤ 300行
- [ ] 大类是否可以拆分为多个小类
- [ ] 是否遵循单一职责原则
- [ ] 是否存在可以提取的公共组件

## 🏗️ 架构设计检查

### SOLID原则遵循
- [ ] **单一职责原则(SRP)**: 每个类/方法只有一个变更理由
- [ ] **开闭原则(OCP)**: 对扩展开放，对修改关闭
- [ ] **里氏替换原则(LSP)**: 子类可以替换基类
- [ ] **接口隔离原则(ISP)**: 不依赖不需要的接口
- [ ] **依赖倒置原则(DIP)**: 依赖抽象而非具体实现

### 设计模式应用
- [ ] 复杂的if-else是否可以用**策略模式**替代
- [ ] 状态转换逻辑是否可以用**状态机模式**管理
- [ ] 复杂流程是否可以用**责任链模式**处理
- [ ] 复杂对象构建是否可以用**建造者模式**
- [ ] 是否正确使用了**单例模式**（GetX服务）

### 模块耦合度检查
- [ ] 模块间是否保持低耦合高内聚
- [ ] 是否正确使用了依赖注入
- [ ] 业务逻辑与UI是否分离
- [ ] 是否避免了循环依赖

## 📝 代码质量检查

### 命名规范
- [ ] 类名使用 PascalCase（如 `ManageTopicController`）
- [ ] 变量/方法使用 camelCase（如 `onCreateTopic`）
- [ ] 私有成员使用下划线前缀（如 `_initData`）
- [ ] 文件名使用 snake_case（如 `manage_topic_controller.dart`）
- [ ] 常量使用 SCREAMING_SNAKE_CASE

### 注释和文档
- [ ] 公共API是否有充分的文档注释
- [ ] 复杂逻辑是否有行内注释说明意图
- [ ] 注释是否与代码保持同步
- [ ] 是否避免了无意义的注释

### 代码风格
- [ ] 是否遵循项目的代码格式规范
- [ ] 是否正确使用了 `const` 构造函数
- [ ] 是否优先使用单引号
- [ ] 是否正确使用了空安全语法

### 错误处理
- [ ] 是否有适当的异常处理
- [ ] 错误信息是否清晰有用
- [ ] 是否避免了捕获过于宽泛的异常
- [ ] 是否正确处理了异步操作的错误

## 🧪 测试相关检查

### 测试覆盖率
- [ ] 新增代码是否有对应的单元测试
- [ ] 测试覆盖率是否 ≥ 80%
- [ ] 关键业务逻辑是否有充分测试
- [ ] 边界条件是否有测试覆盖

### 测试质量
- [ ] 测试是否独立且可重复
- [ ] 测试命名是否清晰表达测试意图
- [ ] 是否避免了测试间的依赖
- [ ] Mock和Stub是否使用得当

## 🚀 性能和安全检查

### 性能优化
- [ ] 是否避免了不必要的重建（使用const）
- [ ] 列表渲染是否使用了适当的优化
- [ ] 是否避免了内存泄漏（工作器销毁）
- [ ] 网络请求是否有适当的缓存策略

### 安全检查
- [ ] 是否避免了硬编码的敏感信息
- [ ] 用户输入是否有适当的验证
- [ ] 是否正确处理了用户权限
- [ ] API调用是否有适当的认证

## 📱 Flutter特定检查

### Widget设计
- [ ] Widget是否保持无状态（优先使用StatelessWidget）
- [ ] 是否正确使用了Key
- [ ] 是否避免了深层Widget嵌套
- [ ] 是否正确使用了BuildContext

### GetX使用
- [ ] 控制器是否正确继承自GetxController
- [ ] 工作器是否在onClose中销毁
- [ ] 是否正确使用了响应式编程（Rx变量）
- [ ] 路由管理是否规范

### 响应式设计
- [ ] 是否使用ScreenUtil进行尺寸适配
- [ ] 是否考虑了不同屏幕尺寸的适配
- [ ] 是否正确使用了.ww和.wh扩展方法

## ✅ 审查完成检查

### 最终确认
- [ ] 所有自动化检查都通过
- [ ] 代码复杂度指标都符合标准
- [ ] 架构设计合理且可维护
- [ ] 代码质量达到项目标准
- [ ] 性能和安全无明显问题

### 改进建议分类

#### 🔴 高优先级（必须修复）
- 圈复杂度 > 10
- 函数长度 > 20行
- 嵌套深度 > 4层
- 安全漏洞
- 测试失败

#### 🟡 中优先级（建议修复）
- 参数数量 > 5个
- 类长度 > 500行
- 重复代码块
- 性能问题
- 测试覆盖率不足

#### 🟢 低优先级（可选优化）
- 命名优化
- 注释完善
- 代码格式调整
- 小的重构机会
