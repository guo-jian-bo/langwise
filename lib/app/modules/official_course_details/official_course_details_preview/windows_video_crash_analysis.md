# Windows 视频连续播放崩溃分析

## 目标与验收口径

- 目标：说明预习页在 Windows 下连续播放大量知识点后崩溃的高概率原因，并给出后续排查与修复方案。
- 验收口径：
  - 能解释为什么当前更怀疑播放器原生资源堆积，而不是磁盘缓存过多。
  - 能说明当前日志已经证明了什么、还不能证明什么。
  - 能给出一条最小范围、可执行的修复路线。

## 修改范围

- 仅新增本文档。
- 不修改任何业务逻辑、播放器逻辑、缓存逻辑。

## 非目标

- 本文档不直接修复崩溃问题。
- 不覆盖“听写核对答案”页面。
- 不讨论图片显示切换问题，该问题已单独处理。

## 兼容性要求

- 后续修复优先限制在 Windows 路径。
- 尽量不影响 macOS / iOS / Android 当前已正常的媒体播放流程。

## 关键边界

- 场景：预习页连续播放几十个知识点后崩溃，用户提供的日志停在第 43~44 次序列附近。
- 当前页面存在“当前视频卡片 + 隐藏预加载卡片”两套视频渲染链路并存。
- 当前缓存包含图片、音频、视频、视频首帧。

## 当前日志能判断什么

### 1. 不是“单纯磁盘缓存无限增长”

项目当前资源缓存走 `ResourceCacheManager.instance.init(basePath: ...)`，没有额外覆写淘汰参数，底层默认：

- `stalePeriod = 7 days`
- `maxNrOfCacheObjects = 1000`

因此缓存会自动淘汰，不是“每播一个知识点就永久追加且绝不清理”。

这不代表缓存完全没影响，但说明“播放到第 43 条就崩”更不像是磁盘文件数量本身导致的立即崩溃。

### 2. 当前日志明确出现了频繁纹理创建

从崩溃前日志可以看到，在一次知识点切换过程中，`media_kit` 连续打印了多次：

- `Create Texture`
- `Free Texture`
- `VideoOutput::~VideoOutput`
- `NativeVideoController: Texture ID`

这说明问题更靠近：

- Windows 下视频纹理 / Surface / NativeVideoController 生命周期
- `Player` / `VideoController` 的原生资源释放节奏

而不是普通的图片、音频文件缓存命中逻辑。

### 3. 当前页面确实同时挂着两套视频链路

预习页当前结构里，除了正在显示的主卡片，还会额外挂一个隐藏的预加载卡片：

- 主卡片：当前知识点播放
- 隐藏卡片：下一知识点预加载

也就是说，在正常流程里，Windows 端不是只有一个视频纹理在工作，而是可能长期存在两套轮换中的原生视频资源。

### 4. 当前“停止”并不等于“释放”

现有控制器大多数切题动作走的是 `stopAndReset()`，它做的主要是：

- pause
- seek
- 状态归零

但它不是 `release()`，不会真正 `dispose player`。

所以从资源角度看，当前代码更像是：

- 频繁停止旧视频
- 保留播放器实例以便复用
- 再继续预加载 / 播放新视频

这在 macOS / iOS / Android 可能没问题，但在 Windows 下更容易形成原生层资源积压。

## 当前日志还不能直接证明什么

虽然方向已经很明确，但只靠这份日志，还不能 100% 直接证明以下任一项：

### 1. 不能直接证明是“哪一个对象没释放”

当前日志里能看到纹理创建和部分释放，但还看不到：

- 当前活跃 `Player` 数量
- 当前活跃 `VideoController` 数量
- 当前是否存在旧 `SequenceTipsVideoWidgetState` 未完全脱钩
- 每次切题后是否发生“旧释放未完成，新实例已创建”的重叠

所以现在是“高度怀疑资源堆积”，但还没法精确到某一个对象。

### 2. 不能直接证明崩溃发生在 Dart 层还是原生层

这份日志最后停在正常播放流程附近，没有明显 Dart exception 栈。

所以更像：

- Windows 原生视频栈崩溃
- 或 Flutter texture / native controller 层异常退出

但还缺少系统崩溃栈或更细的生命周期日志来做最终确认。

### 3. 不能只根据这份日志判断“缓存完全无关”

严格说，磁盘缓存不是当前第一嫌疑，但如果某些缓存命中后的本地路径在 Windows 下触发了不同的播放器行为，缓存也可能是诱因之一。

只是从现有证据看，主因更像“播放器原生资源堆积”，不是“缓存文件过多”。

## 我对根因的判断

### 高概率根因

Windows 下连续切换知识点时，视频预加载与当前播放共存，导致原生视频资源长期高频创建与轮换；而现有切题流程更多使用 `stopAndReset()`，没有及时把旧播放器彻底 `release()`。在播放到几十个知识点后，纹理、surface、native controller 或底层解码资源累积，最终触发崩溃。

### 次高概率问题

`SequenceTipsVideoWidget.didUpdateWidget()` 中，视频源变化后是异步 `unawaited(_releasePlayer(...))`，随后又会继续 `_syncPlayerInitState()`。  
这意味着可能存在一个时间窗：

- 旧播放器还在异步释放
- 新播放器已经开始初始化

如果 Windows 原生层对这种重叠更敏感，就可能加剧资源积压。

### 低概率问题

- 图片缓存导致内存暴涨
- 音频播放器直接导致崩溃
- 单纯磁盘缓存目录过大导致立即闪退

这些目前都不是最符合现象的解释。

## 是否需要补其他日志

### 结论

需要，但不需要大面积加。  
当前日志已经足够支持“先按视频原生资源收敛”的方向，但如果要把根因钉死，建议只补最小一组生命周期统计日志。

### 建议补的日志

1. 每次 `SequenceTipsVideoWidget` 创建 / 释放时，记录：
   - `videoPath`
   - 控制器标识
   - `Player` 是否新建
   - `release` 开始 / 结束

2. 每次预习页切题时，记录：
   - 当前 controller 是 active 还是 preload
   - 本次是 `stopAndReset()` 还是 `release()`
   - `nextVideoPreloadIndex`

3. 每次 source change 时，记录：
   - 旧视频路径
   - 新视频路径
   - 旧 `release` 是否尚未完成

如果这组日志打出来后发现：

- `release` 次数远少于 source change 次数
- 或者连续出现“旧 release 未完成，新 init 已开始”

那根因就基本坐实了。

## 我的解决方案

### 方案一：Windows 下先关闭视频预加载

这是我最推荐的第一步。

做法：

- 仅在 Windows 下关闭“隐藏预加载视频卡片”
- 仅在 Windows 下关闭 `next video preload`
- 保留图片 / 音频 / 视频文件缓存
- 当前知识点视频仍正常播放

优点：

- 改动范围最小
- 最容易验证是否就是“预加载链路”导致的原生资源堆积
- 对业务影响有限，只会损失下一题视频秒开能力

缺点：

- Windows 端视频切题可能会稍慢一点

### 方案二：Windows 下把旧视频控制器从 stopAndReset 提升为 release

做法：

- 切换知识点后，对旧 controller 更积极地 `release()`
- 需要时再重新绑定 / 初始化

优点：

- 可以保留部分预加载策略

缺点：

- 生命周期更复杂
- 容易影响当前已调通的“播放前图片 / 播放中视频 / 播放后图片”切换
- Diff 会明显比方案一大

### 方案三：先关闭 Windows 预加载，再评估是否补强 release

这是我认为最稳的落地顺序：

1. 先在 Windows 下关闭视频预加载
2. 观察是否还会在 40~50 个知识点附近崩溃
3. 如果不再崩溃，说明核心问题基本就在预加载链路
4. 如果仍崩，再继续收紧 `release` 节奏

## 最终建议

基于当前日志，我建议先按下面的策略推进：

1. 不先动缓存策略  
   因为当前证据不支持“缓存淘汰失效”是主因。

2. 优先把问题定义为“Windows 视频原生资源堆积”  
   这和日志里的 `Create Texture / Free Texture / NativeVideoController` 现象更一致。

3. 第一版修复只做 Windows 定向收敛  
   即：关闭 Windows 下的视频预加载，保留文件缓存。

4. 若还需进一步证实，再补最小一组生命周期日志  
   重点不是再看缓存命中，而是看 `Player / VideoController / release` 的闭环。
