# image_picker_utils

## 目标

梳理并收敛 `lib/utils/image_picker_utils.dart` 中分散的图片选择、拍照、裁剪、压缩逻辑，形成一套职责清晰、调用预期稳定的实现结构。

本次先只产出改造清单与实现提示词，不写实现代码。

## 当前问题

### 1. 底层取图能力重复

当前 `pickImage(BuildContext context)` 与 `select({required BuildContext context})` 基本是同一套“相册单选图片”逻辑，只是代码分布在两个方法里，造成：

- 调用方难以判断两者差异
- macOS 目录缓存、权限校验、图片类型校验重复维护
- 后续如果统一调整压缩口径，容易漏改其中一个入口

### 2. 成品图流程重复

当前以下三个方法内部流程高度相似：

- `coursePickImage(...)`
- `courseTakePhoto(...)`
- `selectPicture(...)`

它们本质上都在做：

1. 获取单张图片
2. 可选裁剪
3. 可选压缩
4. 返回最终文件

但目前三条链路是分别写死的，导致维护成本高，也增加了后续调整产物规格时的风险。

### 3. 职责边界混乱

当前文件里同时混杂了三类职责：

- 原始取图：相册单选、拍照、多图选择
- 流程编排：拍照/相册二选一、课程拍照模式、裁剪弹窗
- 文件加工：图片压缩、输出临时文件

这会导致调用方难以预测最终拿到的是：

- 原图
- 裁剪图
- 压缩图

### 4. 压缩语义不稳定

当前 `compressImage(...)` 的实现仍以 `jpeg / jpg` 为默认输出，且参数命名仍是 `minWidth / minHeight`，不符合本次准备统一到“固定宽度 1080、高度自适应、webp 输出”的目标。

### 5. 业务概念下沉过深

`isCoursesBook`、`isCoursesBookFront` 这类业务语义直接进入底层拍照方法，使底层工具层被课程业务耦合。

## 当前方法分层判断

### 一、底层 Raw 取图层

这些方法更适合只负责拿到本地文件：

- `pickImage(BuildContext context)`
- `pickImages({required BuildContext context, int maxSelectCount = 1, int? imageQuality})`
- `takePhotos({required BuildContext context, bool checkCameraPermission = true, bool isCoursesBook = false, bool isCoursesBookFront = false})`
- `select({required BuildContext context})`

其中：

- `pickImage` 与 `select` 需要合并
- `takePhotos` 应收口成原始拍照能力
- `pickImages` 保留多图能力，不和单图成品流混在一起

### 二、成品图流程层

这些方法本质上都在返回“加工后的可上传图片”：

- `coursePickImage(...)`
- `courseTakePhoto(...)`
- `selectPicture(...)`

它们应该统一收敛成一套公共流程，而不是各自维护一遍重复逻辑。

### 三、结果加工层

- `compressImage(...)`
- `ShowCropDialog.show(...)`

它们更适合作为“流程层”的内部步骤，而不是让多条 public 方法分别拼装。

## 建议的目标结构

建议按两层半结构重组：

### 第一层：Raw 原始取图层

职责：

- 权限检查
- 平台差异处理
- 文件存在校验
- 文件类型校验
- macOS 目录缓存与目录访问校验

这一层不负责：

- 裁剪
- 压缩
- 拍照/相册二选一弹窗
- 课程封面业务流程

建议收敛后的语义：

- 相册单选原图
- 相册多选原图
- 拍照原图

### 第二层：成品图流程层

职责：

1. 决定来源：拍照 / 相册 / 弹选择弹窗
2. 调用 raw 层拿原始文件
3. 决定是否裁剪
4. 决定是否压缩
5. 返回最终成品文件

这一层负责“调用方真正想要的一张可上传图片”。

### 第三层：业务语义薄封装

保留少量有业务语义的方法名可以接受，但它们不能再各自维护整套重复流程，只允许薄封装转调统一流程。

例如：

- `selectPicture(...)`
- `coursePickImage(...)`
- `courseTakePhoto(...)`

保留这些名字的目的是让调用处更直观，而不是保留三份相同实现。

## 建议的保留 / 合并 / 下沉清单

### 建议合并

#### 1. `pickImage` + `select`

建议：

- 最终只保留一个“相册单选原图”入口
- `select` 不再作为独立 public 能力长期保留

原因：

- 两者职责相同
- 当前逻辑高度重复
- 后续统一图片规格时不应维护两套近似方法

### 建议保留

#### 2. `pickImages`

建议：

- 继续保留为“相册多图选择 raw 能力”

原因：

- 多图和单图成品流职责不同
- 当前虽然引用不多，但语义清晰，不需要强行并入单图流程

#### 3. `takePhotos`

建议：

- 保留为“原始拍照能力”
- 但职责必须收敛，尽量避免继续向上承载裁剪压缩流程

原因：

- 有 H5 / WebBridge 之类场景直接依赖拍照结果
- 这些调用明显只想拿拍照文件，不想被绑定到通用成品图流程

### 建议收口为薄封装

#### 4. `coursePickImage`

建议：

- 不再保留独立流程实现
- 改为“固定来源 = 相册”的业务薄封装
- 内部统一转调成品图流程层

#### 5. `courseTakePhoto`

建议：

- 不再保留独立流程实现
- 改为“固定来源 = 拍照”的业务薄封装
- 内部统一转调成品图流程层

#### 6. `selectPicture`

建议：

- 保留为主要的单图成品流程入口
- 后续成为统一编排中心

原因：

- 当前最多调用方都更接近“我要一张成品图”
- 它最适合作为统一入口承载拍照/相册二选一、裁剪、压缩

### 建议改造

#### 7. `compressImage`

建议：

- 保留，但职责要明确成“成品图规范化输出”
- 以后不再使用 `jpeg / jpg` 作为默认输出口径
- 以后应明确对齐：
  - 固定宽度 `1080`
  - 高度按比例自适应
  - 不拉伸
  - 不放大
  - 输出 `webp`

## 推荐的最终调用关系

后续改造时，建议统一为下面这套关系：

1. raw 层拿原图
2. 成品流程层决定是否裁剪
3. 如果需要压缩，则只在最终出口做一次规范化
4. 统一返回最终文件

也就是：

- 原图入口永远返回原图
- 成品入口永远返回加工后的最终图片

不允许出现：

- 某些成品入口返回裁剪图
- 某些成品入口返回压缩图
- 某些原图入口偷偷压缩

## 调用方语义判断规则

后续真正改代码时，必须先按调用方意图分流，不能机械替换所有引用。

### 应继续调用 raw 层的场景

满足以下任一条件时，优先使用 raw 层：

- 调用方只需要一个原始本地文件路径
- 调用方后续自己决定是否裁剪或压缩
- 调用方需要保留特殊拍照链路原貌
- 调用方是桥接层 / 中转层 / 上传前自定义处理层

### 应调用成品图流程层的场景

满足以下任一条件时，优先使用成品图流程层：

- 调用方需要“拍照 / 相册”二选一
- 调用方需要统一裁剪
- 调用方需要统一压缩
- 调用方的目标就是拿到一张可直接上传的成品图

## 压缩规格要求

后续实现图片压缩时，必须满足：

- 输出格式统一为 `webp`
- 目标宽度固定 `1080`
- 高度按原图宽高比自适应
- 不允许拉伸
- 不允许裁剪
- 小于等于 `1080` 宽的图片不放大
- 输出写入系统临时目录
- 文件名带唯一标识，避免覆盖

## 裁剪与压缩的关系要求

后续实现时必须明确：

- 如果需要裁剪，应先裁剪，再根据最终裁剪结果做统一压缩
- 不允许在裁剪前后重复压缩两次
- 不允许让某些链路在裁剪后直接返回未规范化产物，而另一些链路返回压缩产物

## 命名建议

本次不要求强制改名，但如果顺手整理命名，建议语义向下面靠拢：

- 相册单选原图：`pickImageRaw`
- 相册多选原图：`pickImagesRaw`
- 拍照原图：`takePhotoRaw`
- 单图成品流程：`selectPicture`

如果当前项目改名成本较高，也可以先保留旧 public 方法名，但内部实现必须已经完成职责分层。

## 实现时必须遵守

- 只做 `image_picker_utils.dart` 图片链路相关整理，不顺手改视频链路
- 不因本次整理去大面积重写调用方业务代码
- 优先保持 public 方法签名稳定，减少影响面
- 先统一职责，再统一压缩规格
- 新增的方法、变量、复杂分支必须补简短注释
- 不允许把底层平台差异、课程相机分支、裁剪压缩逻辑重新揉成新的大方法

## 验收标准

### 结构验收

- `pickImage` 与 `select` 不再并存为两套重复入口
- `coursePickImage` / `courseTakePhoto` / `selectPicture` 不再分别维护完整重复流程
- 原图能力与成品图能力边界明确

### 语义验收

- raw 层调用方拿到的永远是原始文件
- 成品图流程层调用方拿到的永远是最终处理后的文件
- 调用方不需要再猜测返回的是原图、裁剪图还是压缩图

### 规格验收

- 单图成品压缩口径统一到 `1080 webp`
- 高度按比例自适应
- 无格式与扩展名不一致问题
