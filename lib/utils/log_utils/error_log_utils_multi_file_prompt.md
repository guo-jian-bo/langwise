# ErrorLogUtils 改为多文件日志分片写入的实现提示词

请在当前 Flutter 项目中，重构 `lib/utils/log_utils/error_log_utils.dart` 的本地日志落盘方案，将“单文件追加 + 超限后截断文件内容”的实现，改为“多文件分片写入 + 删除最旧整文件”的实现。

本次改造的核心目标只有两个：

1. 日志写入始终保持轻量，永远只做尾部追加写入
2. 日志清理永远不做“删除文件头部内容 / 覆写保留尾部内容”这种重写操作

## 一、必须实现的最终行为

请实现以下日志分片规则：

1. 日志目录仍放在应用私有目录下，由 `ErrorLogUtils` 自己负责创建和维护
2. 每个日志文件最大 `512KB`
3. 所有日志文件总大小最大 `10MB`
4. 当前分片文件写满 `512KB` 后，切换到新的日志文件继续写
5. 当总大小超过 `10MB` 时，按时间顺序删除最旧的整文件，直到总大小重新小于等于 `10MB`
6. 整个实现中，禁止通过“删除文件开头内容”“保留最后 N MB 再覆写原文件”“截断后回写尾部数据”等方式清理日志
7. 日志上传时，不直接上传多个分片文件，而是先把当前所有日志分片按顺序整合成一个临时文件
8. 临时文件只用于上传，上传完成后必须删除

## 二、必须遵守的设计约束

### 1. 性能约束

这是硬要求：

- 不能在主线程执行文件 IO
- 不能每条日志都触发一次全目录扫描
- 不能每次写入都检查所有文件并做重度清理
- 不能读取整份历史日志再决定如何写入
- 不能把日志清理实现成“搬运剩余内容并重写”
- 不能因为日志系统影响页面交互、播放器、网络请求或动画流畅度

推荐方案：

- 使用单例
- 使用单线程串行队列管理所有写入、切片、清理、整合操作
- 每次只做追加写入
- 分片轮转、总量清理、上传整合都走同一条后台串行链路，避免并发竞争

### 2. 文件格式约束

- 每条日志仍然使用单行 JSON
- 文件格式使用 `jsonl`
- 不要改成 JSON 数组
- 文件名应能稳定表达顺序，保证排序后就是写入顺序

建议命名：

- `langwise_log_000001.jsonl`
- `langwise_log_000002.jsonl`
- `langwise_log_000003.jsonl`

如果项目已有更合适的命名方案，也可以调整，但必须满足“按文件名排序即可得到时间顺序”的要求。

### 3. 日志内容约束

保留 `ErrorLogUtils` 现有字段结构和整体使用方式，尽量不影响外部调用方：

- `logError(dynamic error, StackTrace? stackTrace)`
- `logInfo(Object message)`
- `clearErrorLogs()`
- `getLogFileSize()` 或与之等价的统计能力

可以新增私有辅助方法，但应尽量保持外部调用 API 稳定。

同时保留当前“单条日志单行化”的思想：

- JSON 字符串压缩成单行
- 普通文本去掉换行和多余空白
- 避免一条日志跨多行

## 三、推荐的数据与目录设计

请在应用日志目录下使用类似结构：

- `log_segments/`：正式日志分片目录
- `upload_tmp/`：上传用临时文件目录

示例：

- `log_segments/langwise_log_000001.jsonl`
- `log_segments/langwise_log_000002.jsonl`
- `upload_tmp/langwise_log_upload_20260803_153000.jsonl`

要求：

1. 正式日志与上传临时文件分目录存放
2. 上传临时文件不能参与总量统计
3. 删除最旧日志时，只删除正式日志分片，不删除当前正在使用的上传临时文件

## 四、推荐实现方式

### 1. 写入流程

每次 `logError` / `logInfo` 的典型流程应为：

1. 先构造单行 JSON 文本
2. 获取当前可写分片文件
3. 如果当前分片文件不存在，则创建第一个分片
4. 如果当前分片大小 + 本次写入大小 + 换行字节数 > `512KB`，则新建下一个分片
5. 将日志追加写入当前分片末尾
6. 写入完成后，按需执行“总容量清理”

注意：

- 不要在写入前把旧分片内容读入内存
- 不要为了判断是否轮转而遍历每一行
- 只需要依赖文件大小和文件顺序判断是否切片

### 2. 总量清理流程

请实现类似下面的行为：

1. 列出所有正式日志分片
2. 按文件名顺序排序，最旧的在前，最新的在后
3. 统计总大小
4. 如果总大小 <= `10MB`，直接返回
5. 如果总大小 > `10MB`，从最旧文件开始整文件删除
6. 每删除一个文件后重新扣减累计大小
7. 直到总大小 <= `10MB`

注意：

- 删除动作必须是整文件删除
- 不允许部分删除某个分片内容
- 应尽量避免删除当前刚写入的新分片，必要时可保留至少一个最新文件

### 3. 上传整合流程

请新增一个用于上传日志的公开方法，职责如下：

1. 读取当前所有正式日志分片
2. 按顺序将它们整合成一个临时文件
3. 返回这个临时文件给调用方上传

建议方法名：

- `Future<File?> buildUploadTempLogFile()`

要求：

1. 合并顺序必须与原始日志顺序一致
2. 临时文件内容仍是 `jsonl`
3. 不要把所有内容先拼成一个超大字符串再一次性写入内存
4. 应采用流式或分段复制的方式，将多个分片顺序写入到同一个临时文件
5. 如果当前没有任何正式日志分片，可返回 `null`

### 4. 上传完成后的清理方法

请再新增一个公开方法，用于删除上传临时文件。

建议方法名：

- `Future<void> deleteUploadTempLogFile(File? file)`

要求：

1. 只删除上传临时文件
2. 不影响正式日志分片
3. 允许调用方在上传成功后主动调用
4. 即使文件不存在也不要抛出未处理异常

如果你认为更合适，也可以再提供一个包装方法，例如：

- `Future<T> withUploadTempLogFile<T>(Future<T> Function(File file) action)`

即：

1. 先创建临时上传文件
2. 把文件交给上传逻辑使用
3. 上传结束后自动删除临时文件

但无论是否增加包装方法，基础能力必须包含：

- “生成临时上传文件”
- “删除临时上传文件”

## 五、建议保留或调整的方法列表

请至少整理出下面这些能力：

- `Future<void> logError(dynamic error, StackTrace? stackTrace)`
- `Future<void> logInfo(Object message)`
- `Future<void> clearErrorLogs()`
- `Future<int> getLogFileSize()`：返回正式日志分片总大小
- `Future<List<File>> getLogSegmentFiles()`：获取正式日志分片列表
- `Future<File?> buildUploadTempLogFile()`：整合生成上传临时文件
- `Future<void> deleteUploadTempLogFile(File? file)`：删除上传临时文件

其中：

- `getLogFileSize()` 现在不再表示单个文件大小，而是“所有正式日志分片总大小”
- 如果原有 `getLogFile()` 已不适合新架构，可以删除或替换为更明确的方法，比如 `getCurrentSegmentFile()` / `getLogSegmentFiles()`

## 六、异常处理要求

所有日志系统内部异常都必须自行兜底，不能反过来影响业务逻辑：

- 写日志失败不能把业务调用抛挂
- 清理旧文件失败时，至少要保证后续还能继续写日志
- 上传临时文件生成失败时，返回 `null` 或可处理错误，不要造成崩溃
- 删除临时文件失败时，最多 debug 输出，不要影响上传主流程

## 七、兼容性要求

请尽量减少对现有调用方的破坏：

1. `ErrorLogUtils.to.logError(...)` 原有调用方式保持不变
2. `ErrorLogUtils.to.logInfo(...)` 原有调用方式保持不变
3. 原有友盟错误上报逻辑继续保留
4. 原有日志内容字段尽量保留
5. 原有单行化工具方法如 `toSingleLineJsonSafe(...)` 继续保留或保持等价能力

## 八、实现上的明确禁止事项

本次改造中，明确禁止以下做法：

- 禁止继续使用“单文件超过阈值后，保留尾部 N MB 再覆写原文件”的逻辑
- 禁止删除文件前半段内容
- 禁止把一个大文件读入内存后再整体回写
- 禁止每次上传都把全部分片内容一次性拼成一个巨大的字符串
- 禁止在主线程中执行目录扫描、文件复制、文件删除
- 禁止引入数据库、Hive、Isar、SQLite、Room 等存储来替代日志文件分片

## 九、验收标准

实现完成后，应满足下面这些结果：

1. 连续写入大量日志时，只发生追加写与偶发的新分片创建
2. 不再出现“裁剪当前日志文件内容”的实现
3. 日志总量超过 `10MB` 时，会自动删除最旧的完整日志文件
4. 任意时刻正式日志总大小不超过 `10MB`（允许极短时间的写入后清理窗口）
5. 可以生成一个用于上传的临时日志文件
6. 上传完成后可以删除该临时文件
7. 现有业务调用 `logError` / `logInfo` 不需要大面积改动

## 十、请直接输出的内容

请直接基于当前项目代码完成实现，不要只给思路。输出时请至少包含：

1. `lib/utils/log_utils/error_log_utils.dart` 的完整改造
2. 如有必要，补充少量辅助私有方法
3. 说明新增的上传整合方法如何调用
4. 说明如何保证不会再发生“删除文件内容”的高成本操作

本次实现的判断标准很明确：

- 日志永远按分片文件追加写入
- 清理永远通过删除最旧整文件完成
- 上传时通过临时整合文件完成
- 上传结束后删除临时文件
