# video_compress_utils

## 目标

新增一个统一的视频压缩工具 `video_compress_utils.dart`，用于在视频选择与视频录制完成后、文件返回给调用方之前，对本地视频执行统一压缩。

本次只产出设计与实现提示词，不写实现代码。

## 接入位置

需要在以下两个返回点之前接入压缩流程：

1. `lib/utils/image_picker_utils.dart` 的 `selectVideo()` 返回文件之前
2. `lib/utils/image_picker_utils.dart` 的 `recordVideo()` 返回文件之前

目标行为：

- 选择视频后，先校验时长，再压缩，再返回压缩后文件
- 录制视频后，先确认文件存在，再压缩，再返回压缩后文件
- 调用方无需感知压缩细节，仍然只接收 `File?`

## 硬性要求

### 编码与分辨率

- 所有输入视频统一压缩为 `H.265 / HEVC`
- 输出容器统一使用 `mp4`
- 目标宽度固定为 `480`
- 目标高度按原始宽高比自适应计算
- 不允许拉伸
- 不允许裁剪
- 不允许放大
- 小于等于 `480` 宽的视频也统一转码为 `H.265`

### 平台范围

必须支持以下平台：

- iOS
- Android
- macOS
- Windows

### 文件行为

- 输入文件为本地文件
- 输出文件写入系统临时目录
- 输出文件名应带时间戳或唯一标识，避免覆盖
- 压缩成功后返回新的压缩文件
- 压缩失败时返回原始失败语义，不要伪造成功结果

### 业务行为

- 保留原视频时长，不裁剪时长
- 保留音频轨道
- 如果原文件不存在，直接返回 `null`
- 如果压缩结果文件不存在或大小异常，视为压缩失败

## 推荐实现方向

### 推荐方案

优先采用统一的 FFmpeg 转码方案，由 `video_compress_utils.dart` 对上层屏蔽平台差异。

原因：

- 目标非常明确：`480` 宽、等比缩放、统一转为 `H.265`
- 需要覆盖 iOS / Android / macOS / Windows 四端
- 需要稳定控制编码格式、分辨率、输出容器与音频处理策略
- 播放器能力不等于转码能力，当前项目已有 `video_player / media_kit` 更偏播放，不适合直接承担压缩职责

### 编码策略

优先级建议如下：

1. 统一封装一个公共压缩入口
2. 内部使用 FFmpeg 执行转码
3. 输出统一为 HEVC + MP4
4. 缩放策略固定为宽度 `480`，高度按比例自动计算并保证为偶数

### 分辨率规则

实现时必须确保输出宽高满足编码器要求：

- 输出宽度固定 `480`
- 输出高度根据原始比例计算
- 输出高度必须处理成偶数

如果输入宽度本来小于等于 `480`：

- 仍然执行一次转码
- 但不要放大分辨率
- 分辨率应保持原尺寸，或者在不放大的前提下按编码要求做最小必要修正

这次需求里“统一都转”的重点是统一转成 `H.265`，不是强制把小视频放大到 `480`

## 工具职责建议

建议新增工具文件：

- `lib/utils/video_compress_utils.dart`

建议对外暴露单一入口，例如语义类似：

- 压缩单个本地视频并返回压缩后的文件

不建议把压缩逻辑直接堆进 `image_picker_utils.dart`，应拆到独立工具类中，保证：

- `image_picker_utils.dart` 只负责编排“选择/录制 -> 校验 -> 压缩 -> 返回”
- `video_compress_utils.dart` 只负责“读取输入 -> 转码 -> 校验输出 -> 返回结果”

## 建议的压缩流程

### 选择视频链路

1. 用户选择视频
2. 校验文件存在
3. 校验视频时长是否超过 `maxDuration`
4. 调用统一视频压缩工具
5. 返回压缩后的文件

### 录制视频链路

1. 用户录制视频
2. 校验文件存在
3. 调用统一视频压缩工具
4. 返回压缩后的文件

## 音视频参数建议

### 视频

- 编码：`H.265 / HEVC`
- 质量策略：优先使用可控质量方案，避免纯固定码率
- 输出帧率：默认跟随源视频，除非后续业务明确要求降帧
- 像素格式：选择兼容主流移动端和桌面端播放的安全格式

### 音频

- 保留原音频轨
- 若需要重编码，优先使用 `AAC`
- 音频码率可控制在中等水平，避免音频体积反而过大

## 失败处理要求

- 压缩命令执行失败时，明确记录失败日志
- 输出文件不存在时，视为失败
- 输出文件大小为 `0` 时，视为失败
- 失败后不要返回一个不存在的临时文件
- 上层可根据失败结果决定 toast 文案，但压缩工具内部应尽量返回清晰的失败语义

## 日志与调试要求

- 记录输入文件路径
- 记录输入文件大小
- 记录输入分辨率
- 记录输入时长
- 记录输出文件路径
- 记录输出文件大小
- 记录输出分辨率
- 记录耗时

日志应便于后续排查以下问题：

- 某平台压缩失败
- 某些视频无法读取分辨率
- 某些视频压缩后无声音
- 小尺寸视频被错误放大
- 竖屏视频被错误拉伸

## 验收标准

### 功能验收

- `selectVideo()` 返回前会完成压缩
- `recordVideo()` 返回前会完成压缩
- 四端都能执行压缩
- 输出视频编码为 `H.265`
- 输出文件可被项目现有播放器正常播放

### 分辨率验收

- 宽度大于 `480` 的视频，输出宽度为 `480`
- 高度按比例缩放，无拉伸、无裁剪
- 小于等于 `480` 宽的视频，不放大，但仍统一转为 `H.265`

### 稳定性验收

- 压缩完成后返回的文件真实存在
- 连续多次选择/录制不会出现临时文件命名冲突
- 大多数常见输入格式可正常转码：`mp4`、`mov`、`m4v`

## 实现边界

- 本次实现只处理本地单文件压缩
- 不在 `image_picker_utils.dart` 中堆放底层转码细节
- 不提前扩展批量压缩、断点恢复、上传联动等非当前需求能力
- 不顺手改动与本次需求无关的图片选择、图片压缩逻辑

## 本次实现时必须遵守

- 先新增独立工具 `video_compress_utils.dart`
- 再在 `image_picker_utils.dart` 的两个视频返回点接入
- 保持现有方法签名尽量稳定
- 只做本次需要的最小改动
