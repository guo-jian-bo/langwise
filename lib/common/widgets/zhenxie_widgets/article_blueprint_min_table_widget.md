# ArticleBlueprintMinTableWidget / ArticleBlueprintMaxTableWidget 连线实现提示词

## 目标

请在 Flutter 组件 `ArticleBlueprintMinTableWidget` 中，为“篇章蓝图最小路径表”补上**正文分支之间的链接线**。

同一文件里如果还有 `ArticleBlueprintMaxTableWidget`，两者的路径语义必须保持一致：

- 最小表：偏概览卡片
- 大图表：偏详情卡片
- **连线算法、节点规则、箭头规则必须共用同一套**
- 允许 UI 体量不同，但不允许两套表各自长出一套不同的路径判断逻辑

这次改动的目标非常明确：

1. **保留现有 UI 结构不重画**
2. **保留现有逻辑结构不改写**
3. 在现有四列起承转合卡片之间补出“路径流向”
4. 视觉语义对齐 Web 端篇章蓝图路径图
5. 只新增当前组件需要的连线能力，不顺手改造成另一套组件体系

当前 Flutter 组件已经把以下部分画好了：

- 顶部 `正文里可以加小标题`
- 文首格式 / 文尾格式卡片
- 顶部四拍圆点和横向节奏线
- 每一拍下面的候选段型卡片
- `或` 分隔
- 空拍 / 可选 / 必写三种状态样式

这次要补的是：

- **候选段型卡片之间的跨列路径连线**
- 以及右侧的**目标箭头**

不要改成全新布局，也不要把当前组件推倒重做成 Web 一模一样的 DOM 结构。

这次实现的硬边界再强调一次：

- **所有现有 UI 都不要动**
- **所有现有业务逻辑都不要动**
- **只允许增加“链接线绘制所必需”的最小增量代码**

所谓“最小增量代码”只包括：

- 连线层本身
- 为了拿到卡片坐标而新增的 key / 测量逻辑
- 为了把节点关系喂给 painter 而新增的内部路径数据整理
- 为了让最小表和大图表复用而抽出的内部工具方法

除此之外，不允许顺手调整：

- 卡片样式
- 间距
- 排版
- 文案
- 状态枚举语义
- 现有顶部节奏线逻辑
- 文首文尾显示逻辑

也就是：

- **上面一层是节奏骨架**
- **下面一层是正文路径分支**

两层语义不要混。

## 实现边界

### 要做

1. 根据每拍 `allowedParagraphs` 生成路径节点
2. 根据拍状态生成跨列连线
3. 支持：
   - 正常前进连线
   - 可选拍跨越连线
   - 空拍跳过
   - 多个候选段型之间的多对多连线
4. 连线要跟随布局真实位置，不写死坐标
5. 数据变化、屏幕尺寸变化后，连线要能重新计算

### 不做

1. 不重构整个组件树
2. 不改现有 UI 结构和样式
3. 不改现有业务逻辑和状态语义
4. 不改成新的页面级组件
5. 不给文首 / 文尾格式补路径连线
6. 不引入点击选中、闪烁、hover 等交互
7. 不做篇实例详情页那套“选中金边 / flashNodeId / usedNodeIds”
8. 不额外补业务状态管理

## 路径语义必须对齐 Web

### 一、节点来源

每一拍的节点来自：

- `ArticleBlueprintEntityBlueprintsSlots.allowedParagraphs`

每个候选段型卡片都视为一个路径节点。

节点显示仍然沿用你现在已有卡片内容：

- 段型名：`paragraphType.name`
- 用途名：`usageName`

### 二、拍状态来源

每拍状态来自：

- `slot.statusEnum`

含义：

- `required`：该拍要写
- `optional`：该拍可写可不写
- `empty`：该拍空着，不参与路径节点

### 三、空拍规则

若某拍：

- `repeatMax <= 0`
- 或 `allowedParagraphs` 为空

则视为没有可连接节点。

这类拍：

1. 顶部现有 header 仍按当前 UI 展示状态
2. body 区域不产生路径节点
3. 不参与节点间连线

### 四、正常连线规则

对于两个相邻的**有效拍**：

- 当前拍每个节点
- 都要连到下一拍每个节点

也就是**多对多全连接**。

示例：

- `opening` 有 2 个候选
- `develop` 有 3 个候选

则需要画 6 条线。

### 五、可选拍跨越规则

这里必须对齐 Web 端 `compositionPathModel(...)` 的逻辑。

规则不是“只连到最近一拍”。

正确逻辑是：

1. 从当前有效拍出发，先连接到下一个有效拍
2. 如果这个“下一个有效拍”是 `optional`
3. 那么还要继续向后找
4. 再额外补一组“跨过这个 optional 拍”的 bypass 连线
5. 一直补到遇见第一个非 optional 的有效拍为止

也就是说：

- 当前拍 -> 可选拍：画正常实线
- 当前拍 -> 可选拍后面的下一有效拍：再画一组“跨越线”

如果连续多个可选拍，就继续向后补跨越线。

### 六、跨越线样式

跨越 optional 拍的那组线：

- 不要和正常实线完全一样
- 要明显看得出是“绕过可选拍”的路径

建议：

- 虚线
- 或更柔和的颜色
- 或稍微向上拱起的曲线

这点对齐 Web 端 `bypass` 语义。

### 七、箭头规则

当前实现如果需要箭头，必须遵守下面三条：

1. 箭头只出现在**目标侧**
2. 箭头方向要跟随曲线靠近终点那一小段的真实走势，不能写死成水平朝右
3. 同一个目标卡片如果有多条入线，**只允许保留一个箭头**

也就是说：

- 单条入线：单线 + 单箭头
- 多条入线：多条线先汇入共同尾点，再接一个共享箭头

不要为每条入线都各自画一个箭头，否则会糊成一团，看不出箭头形状。

## 推荐的 Flutter 实现思路

## 1. 继续复用现有 UI，外面包一层 Stack

最稳妥的做法是：

1. body 区域外层用 `Stack`
2. 先放你现在已有的四列卡片内容
3. **最上层**放 `CustomPaint`

也就是：

- 卡片照常铺
- 连线层盖在最上面，但通过 `IgnorePointer` 不拦截点击

这样不会破坏已有卡片样式，也不需要把卡片内容绘制进 painter。

注意这里的“包一层 `Stack`”是**增量包裹**，不是重排现有节点层级。

目标应该是：

- 原来的卡片怎么渲染，仍然怎么渲染
- 原来的方法拆分和调用顺序，尽量保持不变
- 只是在合适位置加一层连线画布

### 为什么用 `Stack + CustomPaint`

因为连线依赖的是：

- 左右两列卡片的真实布局位置

这些位置只有在布局完成后才能得到。

所以不要写死：

- 第几列从哪到哪
- 每条线高度固定多少

必须走“先布局、再测量、再画线”。

### 一个后来验证过的关键点

**连线层不能放在内容下面。**

如果 `CustomPaint` 在卡片层下方，会出现：

- 卡片 body 把线盖住
- 视觉上像“线断了”或“线钻到卡里不见了”

所以最终层级必须是：

1. 卡片内容
2. `Positioned.fill + IgnorePointer + CustomPaint`

---

## 2. 用 GlobalKey 测量每个候选卡片的位置

每个候选段型卡片外层都要包一个可测量节点。

建议给每个节点建立稳定 key，至少包含：

- `beatNid`
- `paragraphTypeNid`
- `index`

为什么要加 `index`：

- 同一拍理论上可能出现重复类型
- 只用 `paragraphTypeNid` 不够稳

测量目标是卡片容器本身，不是里面的 `Text`。

需要拿到：

1. 卡片在 body 连线画布坐标系中的 `Rect`
2. 右侧中点作为出线点
3. 左侧中点作为入线点

### 不要测量这些对象

不要去测：

- `ListView.separated` 的整体高度作为节点
- `Expanded` 列宽本身
- `ParagraphRhetoricalContainerWidget` 顶部圆点

路径节点就是“每一张候选段型卡片”，不是列容器。

---

## 3. 建议先做一层内部路径模型

虽然这次只是一个组件，但仍建议先整理一层内部轻量路径模型，避免把绘制逻辑直接写死在 Widget 树里。

建议至少拆出这几类内部数据：

### 路径节点

包含：

- 唯一 id
- 所属 `beatNid`
- 所属列 index
- 所属候选项 index
- 绑定的 `allowedParagraph` 数据
- 对应的 `GlobalKey`

### 路径边

包含：

- `fromNodeId`
- `toNodeId`
- `kind`

其中 `kind` 至少区分：

- `forward`
- `bypass`

### 已布局边

在拿到坐标后，再生成用于 painter 的布局对象，包含：

- start
- end
- control1
- control2
- kind
- color
- targetNodeId（供“多条入线汇成一个箭头”分组）

---

## 4. 生成边的算法

建议严格按下面步骤：

### 第一步：按四拍顺序整理列

顺序固定：

1. `opening`
2. `develop`
3. `turn`
4. `close`

不要按接口原数组顺序直接信任渲染，先整理成固定拍序。

### 第二步：为每拍生成节点列表

每拍：

- 若为空拍或没有 `allowedParagraphs`，节点列表为空
- 否则按当前 UI 渲染顺序生成节点

### 第三步：只保留有效拍用于路径推导

有效拍定义：

- 节点列表非空

### 第四步：按 Web 逻辑推导边

伪规则：

1. 遍历每个有效拍 `layer`
2. 找它后面第一个有效拍，补 `forward` 边
3. 如果这个目标拍是 `optional`
4. 继续往后找下一个有效拍
5. 从当前 `layer` 再补一组 `bypass` 边
6. 持续到遇到首个非 optional 的有效拍为止

### 第五步：每组边内部采用全连接

例如：

- from 层 2 个节点
- to 层 3 个节点

则生成 6 条边。

## 5. 连线路径形态建议

优先参考 Web 端 `CompositionBeatGrid.tsx` 的 cubic bezier 方案。

### 普通 forward 线

建议：

- 从左节点右侧中点出发
- 到右节点左侧中点结束
- 中间用平滑三次贝塞尔曲线
- 曲率适中，不要做死板折线

### bypass 线

建议：

- 仍然使用贝塞尔
- 但在控制点 Y 上做一点额外偏移
- 让跨越线轻微拱起
- 避免和普通 forward 线完全重叠

这和 Web 里的 `bulge` 是同一思路。

### 目标端箭头

如果业务视觉已经要求加箭头，则建议：

- 使用实心箭头
- 箭头尺寸略小
- 箭头尖端贴目标卡片左侧
- 线身在箭头尾心处提前收住，再接箭头

这样线和箭头的衔接会更圆滑。

### 不推荐

不建议做成：

- 生硬的直角折线
- 所有线都走同一条中轴
- 每条线都叠在一起完全不可分辨

---

## 6. 连线颜色和样式建议

连线颜色建议跟随**目标拍**颜色，而不是统一灰线。

目标拍颜色可直接复用：

- `ParagraphRhetoricalEntityList.colorValue`

也就是：

- 连到 `develop` 的线，用 `develop` 的色系
- 连到 `turn` 的线，用 `turn` 的色系

### 推荐样式

#### forward

- 实线
- `strokeWidth` 约 `1.5.wMin`
- `StrokeCap.round`
- 透明度约 `0.45 ~ 0.65`

#### bypass

- 虚线
- 或更低透明度
- 同时稍微抬高弧线

### 关于箭头的补充口径

最初如果只是验证路径关系，可以先不加箭头。

但如果视觉已经明确要求箭头，那么后续实现口径应以上一节为准，不要再退回“完全不做箭头”的方案。

## 7. 现有布局下的关键注意点

### 一、所有列高度已经被 `maxLength` 对齐

当前 `_buildItemContentWidget(...)` 里有：

- `allHeight = maxLength * 88.wMin + (maxLength - 1) * 36.wMin`

这很好，说明四列 body 高度已经对齐。

因此连线层的计算基准应该建立在这块对齐后的区域上，不要另外推导一套虚拟网格。

### 二、每列内部 `ListView.separated` 只是静态排布

这里虽然用了 `ListView.separated`，但：

- `shrinkWrap: true`
- `NeverScrollableScrollPhysics()`

所以它本质上是一个定高静态列表。

后续测量每个 item 的 `Rect` 是可行的。

### 三、空拍卡片也有占位高度

`allowedParagraphs.isEmpty` 时，当前实现会渲染一个居中的空态卡片。

这里要分清两件事：

1. **视觉占位**可以保留
2. **路径节点**不要把空态占位算进去

也就是说：

- 空拍列有 UI 占位
- 但不参与路径连线

### 四、顶部 header 和 body 连线不要互相覆盖

建议把 body 连线 painter 放在：

- 候选段型卡片区域内部

不要把画布高度扩到顶部 header 区，否则容易和现有圆点横线重叠。

## 8. 建议的代码组织方式

请保持“外科手术式改动”，不要全文件推翻重写。

推荐拆分方向如下：

### 组件状态层

在 `ArticleBlueprintMinTableWidget` 或其内部私有区域维护：

- 节点 key 映射
- 已测量的路径布局数据

如果能不新增页面级对外状态，就不要新增。

如果能只放在组件内部私有实现，就不要上提到公共层。

### 纯计算方法

建议拆私有方法：

1. 根据 `slots` 生成拍层数据
2. 根据拍层数据生成边
3. 根据 key 测量节点坐标
4. 把边转换成 painter 可用布局对象

### 工具类复用

如果同文件同时存在最小表和大图表，建议把下面这些公共方法抽到：

- `ArticleBlueprintTableUtils`

适合放进去的包括：

1. 路径节点 id 生成
2. 节点 `GlobalKey` 复用
3. 路径层生成
4. 路径边推导
5. 节点坐标测量
6. 边布局生成
7. 布局相等判断

这样可以保证：

- 两个表的路径语义完全一致
- 不会出现一个表修了逻辑，另一个表漏改
- 后续只维护一套路径算法

### 绘制层

新增一个私有 `CustomPainter`，只负责画线，不负责业务数据推导。

### 注释要求

因为这个区域后续维护成本高，所有新增的：

- 私有数据类
- 路径计算方法
- 坐标测量方法
- painter

都必须补简短注释，说明：

- 这个结构存什么
- 这个方法在哪个阶段调用
- 为什么要这样计算

## 9. 推荐的验证场景

实现后至少自测下面几种情况：

### 场景 1：四拍都只有一个节点

预期：

- 每列之间各一条平滑实线

### 场景 2：某拍有多个候选节点

预期：

- 当前拍到下一拍是多对多全连接
- 线不会明显错位到文字中间

### 场景 3：中间拍是 optional

预期：

- 当前拍 -> optional 拍有正常实线
- 当前拍 -> optional 后一拍还有 bypass 虚线

### 场景 4：中间拍 empty

预期：

- empty 列不产生节点连线
- 前后有效拍直接建立连接

### 场景 5：窗口尺寸变化 / 父布局变化

预期：

- 连线会重新跟随节点位置
- 不出现旧位置残留

### 场景 6：文首 / 文尾显示与否变化

预期：

- 只影响整体竖向布局
- body 区域连线仍能重新测量并正确贴合

## 10. 最终落地标准

完成后的 Flutter 组件应满足：

1. 一眼能看出四拍候选段型之间的流向
2. 可选拍既能接入主路径，也能被绕过
3. 空拍不制造伪路径
