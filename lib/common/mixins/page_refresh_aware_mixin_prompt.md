# PageRefreshAwareMixin 设计提示词

你是一个资深 Flutter / GetX 工程师。请在当前项目中设计并实现一个**通用页面刷新感知 mixin**，用于让页面控制器在运行过程中接收统一的刷新通知，并在不同刷新时机执行自定义逻辑。

本次先明确设计目标与实现边界，后续编码必须严格遵守本提示词，不允许脱离这里的约束自行扩展。

## 一、目标

新增一个通用 mixin，暂定命名为：

- `PageRefreshAwareMixin`

它的职责不是面向“全局设置”单一业务，而是面向**页面中途刷新能力**：

- 当前页处于可立即处理状态时，接到通知后立即刷新
- 当前页是父页面，用户从下级页面 `back` / `pop` 返回后再刷新

这个 mixin 是后续可复用的页面级通用能力，不局限于设置变更场景。

## 二、适用场景

至少支持以下场景：

1. 全局设置改变后，当前页需要重新拉接口
2. 从子页面返回父页面后，父页面需要重新拉接口
3. 后续其他业务触发的页面刷新诉求

注意：

- 本次不按“哪一种设置被修改”区分回调
- 本次只按“刷新时机”区分回调

## 三、命名要求

本次不要使用 `SettingAwareMixin` 这类过于业务化的名字。

统一使用或保持接近以下语义：

- `PageRefreshAwareMixin`

命名重点是表达“页面感知刷新信号”，而不是“设置监听”。

## 四、职责边界

`PageRefreshAwareMixin` 只负责：

1. 接收统一的页面刷新通知
2. 判断页面当前是否适合立即处理
3. 在恰当时机触发页面实现的自定义回调
4. 在生命周期结束时释放自身监听资源

`PageRefreshAwareMixin` 不负责：

1. 具体业务接口怎么请求
2. 页面首次进入时的初始化加载
3. 按设置项种类细分通知
4. 管理面包屑、路由标题、页面业务状态

不要把它和 `RoutesBreadcrumbMixin`、`DualBreadcrumbMixin` 合并成一个大 mixin。

正确方向是让页面按需组合：

```dart
class XxxController extends GetxController
    with DualBreadcrumbMixin, PageRefreshAwareMixin
```

或：

```dart
class XxxController extends GetxController
    with RoutesBreadcrumbMixin, PageRefreshAwareMixin
```

## 五、回调设计

本次只需要两个不同刷新时机的回调，不需要更多细分类别。

### 1. 立即刷新回调

用于：

- 当前页面正在前台
- 接到刷新通知后，需要立刻重新拉接口或执行刷新逻辑

### 2. 返回后刷新回调

用于：

- 用户从下级页面 `Get.back()` / `Navigator.pop()` 返回当前页面后
- 当前页面在恢复展示时再执行刷新逻辑

注意：

- 两个回调允许同时存在
- 如果某个页面两个回调都实现了，说明该页面就是明确需要两种刷新行为
- **不要做互斥，不要自动去重**

也就是说：

- 同一次通知可以同时命中“立即刷新”与“返回后刷新”两类处理
- 是否特殊处理由页面自己决定

## 六、并发与丢弃规则

页面刷新大概率会重新拉接口，因此回调默认按异步场景设计。

必须遵守以下规则：

1. 如果页面当前正在执行一次刷新任务
2. 在刷新未结束前又收到新的刷新信号
3. **后续信号直接丢弃**

不要排队，不要合并，不要补执行最后一次。

这是硬要求。

## 七、页面接入方式

这个 mixin 是**按需接入**，不是全项目强制接入。

判断原则：

### 需要接入

- 页面在收到刷新通知后要重新拉接口
- 页面在从子页面返回后要补刷新
- 页面存在明确的页面级副作用刷新行为

### 不需要接入

- 页面只是直接读响应式状态并自动重建 UI
- 页面没有额外的数据请求或副作用

不要为了“统一”而让所有控制器都 `with` 它。

## 八、生命周期边界

本 mixin 只处理**页面运行过程中**的刷新通知。

必须明确：

- **页面首次进入不算这套自定义刷新生命周期的一部分**
- 首次加载由页面自己的 `onInit` / 初始化逻辑决定
- mixin 不替代页面原本的初始化流程

## 九、页面可用性判断

必须考虑页面是否仍然可处理通知。

实现时需要满足：

1. 页面销毁后不再执行任何刷新回调
2. 页面已经不可用时不再处理通知
3. 只有页面还活着、且满足当前触发时机时，才执行对应回调

不要假设通知发出时页面一定还存在。

## 十、返回后刷新定义

本次“返回后刷新”的定义已经明确：

- 指用户从别的页面 `back` 回来
- 或者 `pop` 回来

也就是：

- 当前页面先进入下级页面
- 下级页面关闭后
- 当前页面重新成为可见页面
- 此时触发“返回后刷新回调”

不要把它理解成普通 rebuild，也不要把它理解成首次进入页面。

## 十一、通知机制与入口约束

本次不单独新建“刷新中心”文件。

统一采用**mixin 文件内聚实现**的轻量方案：

1. 在 `PageRefreshAwareMixin` 所在文件内维护页面注册表
2. 在同一个文件内提供统一的通知入口
3. 外部通过统一入口发通知
4. 由 mixin 内部将通知分发给已接入页面

注意：

- 这里虽然对外表现为“调用 mixin 的专门通知方法”
- 但本质上不是外部直接拿某个页面实例然后调用它的实例方法
- 而是通过 mixin 文件内的统一入口 + 注册表完成分发

这样做的原因是：

- 通知源不止一个
- 页面实例可能有多个
- 页面存在可见、不可见、销毁等状态
- 外部不适合直接持有并管理页面实例

### 通知入口要求

通知入口需要支持：

1. 无 key 通知
2. 带 key 通知

语义要求：

- `key == null`：表示全局通知
- `key != null`：表示按 key 定向通知

### key 设计要求

本次 key 不使用 route、tag 的默认推导方案。

同时，本次**不要为页面单独设计 `getter` 形式的刷新 key 声明**。

统一采用：

- 通知入口接收可选 `key`
- mixin 在分发时，将该 `key` 作为参数透传给页面刷新回调

也就是说：

- 页面是否关心某个 key，由页面在自己的回调实现中决定
- 页面不需要额外实现一个专门的 `pageRefreshKey` getter

这样更轻，也更符合你当前希望减少额外声明的方向。

### 通知源通用性要求

虽然本次不拆独立刷新中心文件，但仍然必须保证通知入口具备通用性。

禁止把通知能力写死在某一个 widget 中，例如：

- 不能只依赖 `general_setting_button_widget.dart` 作为唯一触发入口

后续其他页面、控制器、弹窗、公共组件，也都应该能通过统一入口触发刷新通知。

## 十二、页面可见与不可见时的通知处理规则

收到通知后，页面处理规则必须统一。

### 1. 页面当前可见

当页面当前处于可立即处理状态时：

- 如果当前不在刷新中，立刻触发“立即刷新回调”
- 如果当前正在刷新中，后续信号直接丢弃

注意：

- 在这条规则下，一次通知命中“立即刷新”后，不会天然再继续命中“返回后刷新”
- 也就是说，**一条通知只命中一种时机**

### 2. 页面当前不可见

当页面当前不可见时：

- 不立刻执行刷新
- 只记录一个“待返回刷新”标记

注意：

- 不可见期间如果收到多次通知，不累计次数
- 不排队，不补执行多次
- 只保留一个“回来后刷新一次”的状态

这意味着：

- 页面不可见期间设置改了 1 次，回来刷新 1 次
- 页面不可见期间设置改了 10 次，回来也只刷新 1 次

这条规则是为了避免页面恢复可见后重复拉接口。

## 十三、返回后刷新识别方式

本次“从下级页面返回”的识别方式已经确认：

- 直接基于项目现有的 `AppPages.observer`
- 页面通过 `RouteAware` 感知路由前后台切换

参考入口：

- `lib/main.dart` 中注册的 `AppPages.observer`

推荐语义：

- 页面被下级页面覆盖：`didPushNext()`
- 下级页面返回当前页面：`didPopNext()`

其中：

- “返回后刷新回调”的触发时机，就是页面在 `didPopNext()` 中重新变为可见时

不要再另外实现一套路由恢复判断逻辑。

## 十四、实现风格要求

必须遵守当前项目规范：

1. 保持改动聚焦，不做无关重构
2. 命名清晰，避免过度抽象
3. 方法和关键状态都要补简短注释
4. 不要为了“复用”把能力做成过大的总线型巨型 mixin
5. 不要把面包屑能力、页面刷新能力、业务接口能力混到一起
6. 如果 mixin 覆写 `onInit` / `onClose`，必须认真处理 `super` 调用链
7. 控制器资源监听必须在 `onClose` 释放

## 十五、页面侧语义要求

页面接入后，应当能清晰表达以下语义：

- 这个页面是否需要立即刷新
- 这个页面是否需要返回后刷新
- 回调中收到的通知 `key` 是什么

不要强迫所有页面都必须实现两个回调。

应该允许：

1. 只处理立即刷新
2. 只处理返回后刷新
3. 两者都处理

页面如果需要区分来源作用域，应当直接根据回调参数中的 `key` 做判断，而不是额外声明页面级 getter。

## 十六、本次已确认规则清单

以下规则已经确认，后续编码时不得擅自改动：

1. mixin 名称方向改为“页面刷新感知”，不要限定为设置监听
2. 只按刷新时机划分回调，不按设置类型划分
3. 需要两个回调：
   - 立即刷新
   - 返回后刷新
4. 两个回调允许同时命中
5. 不做自动去重
6. 如果页面正在刷新，后续刷新信号直接丢弃
7. 初次进入页面不算这套自定义刷新能力的一部分
8. 页面销毁后不执行回调
9. 返回后刷新明确指从下级页面 `back` / `pop` 回来
10. 不单独新建刷新中心文件，通知入口和注册表都收敛在 mixin 文件内
11. 外部不直接持有页面实例调用实例方法，而是通过 mixin 文件内统一入口分发
12. 通知入口支持可选 key
13. `key == null` 表示全局通知，`key != null` 表示定向通知
14. 不为页面单独设计刷新 key getter，通知 key 直接通过回调参数透传
15. 页面不可见期间收到通知时，不立即刷新，只记录一个待返回刷新标记
16. 页面不可见期间多次收到通知，不累计，只在返回后刷新一次
17. 一条通知只命中一种时机，不做“立即刷新 + 返回后刷新”的天然双命中
18. 从下级页面返回的识别方式，统一基于 `AppPages.observer` + `RouteAware`

## 十七、禁止事项

后续编码时禁止出现以下实现倾向：

1. 把该能力写死成“全局设置专用”
2. 只在某一个设置弹窗里发通知，导致其他入口失效
3. 把页面刷新能力和面包屑 mixin 强耦合
4. 为了省事让所有页面强制接入
5. 在一个刷新尚未结束时继续串行执行后续刷新
6. 把首次进入页面误算成返回后刷新
7. 在页面销毁后继续触发异步回调
8. 直接使用 route 或 tag 作为强制默认 key，限制页面自定义能力
9. 强制页面额外声明专门的刷新 key getter
10. 页面不可见期间每次收到通知都累计成多次返回刷新
11. 另起一套独立的重型刷新中心架构

## 十八、后续编码前仍需再次确认的事项

虽然本次已经明确了大部分边界，但真正写代码前仍需重新核对以下技术落点：

1. mixin 文件内统一通知入口的具体命名方式
2. 两类回调的具体签名如何设计，才能自然接收通知 `key`
3. 两类回调的默认空实现方式如何定义，才能既清晰又不增加页面接入负担

注意：

- 这三项属于实现落点确认
- 不属于本次需求方向本身的争议项
- 在没有最终确认前，不要擅自选一个重型架构方案
